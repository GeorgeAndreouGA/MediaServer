# Reverse Proxy Architecture (DMZ + Internal)

> **Golden rule:** admin functionality for any site is reachable **only** through the internal server, from LAN or VPN clients. The DMZ server — the one facing the public internet — must never be able to reach an admin route, full stop. No public client ever gets a path to admin, even indirectly.

## The two tiers

There are two nginx roles in this setup, each with its own config, and they are never the same machine for public sites:

| Tier                      | Role                                                                             | Reachable from                                                                                            |
| ------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **DMZ proxy**       | Sits in a DMZ segment, out of the LAN, facing the public internet via Cloudflare | The public internet (via Cloudflare only)                                                                 |
| **Internal server** | Runs the actual app / serves the real content                                    | The DMZ proxy (for public routes)**and** LAN/VPN clients directly (for everything, including admin) |

### Request chains

```
Public client:  Cloudflare → [DMZ proxy :443]      → [Internal server :443] → App
Admin/LAN:      LAN or VPN client                  → [Internal server :443] → App
```

The DMZ never talks to admin routes, and public clients never reach the internal server directly — they only ever arrive via the DMZ. Reference configs: `proxy_nginx_dmz.conf` (DMZ) and `internal_nginx_on_server_for_dmz_proxy.conf` (internal).

## How the golden rule is enforced

Every admin location is defined on **both** configs, but with opposite behavior:

| Location                                      | On the DMZ proxy                                 | On the internal server                                               |
| --------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| `/music/admin`, `/music/api/admin`        | `return 403;` — hard-blocked, unconditionally | `allow <LAN/VPN ranges>; deny all;` then `proxy_pass` to the app |
| `/music/audio/`, `/music` (public routes) | `proxy_pass` to the internal server            | `proxy_pass` to the app                                            |

The DMZ doesn't even attempt to forward admin requests — it kills them immediately. The internal server is the only place admin ever resolves to a real backend, and even there it's gated by an IP allow-list scoped to LAN subnets and VPN client ranges (see [VPN (Tailscale)](<../Server set Up ( Do first )/6. vpn ( tailscale ).md>)). If you're auditing "can the public reach admin," the answer only needs to be checked in one place: the DMZ config's `403`.

Additionally, the DMZ restricts *who* it accepts connections from in the first place — only Cloudflare's published IP ranges are allowed through (checked via a `geo` map and `real_ip_header CF-Connecting-IP`), so even the public routes on the DMZ can't be hit by bypassing Cloudflare directly.

## The rule that keeps the two configs in sync: matching block names

> **The DMZ proxies location-by-location, not as a blanket passthrough.** Because of that, every `location` path that exists on the DMZ config must exist under the **exact same path** on the internal config.

For example, `location /music/audio/` must be spelled identically in both `proxy_nginx_dmz.conf` and `internal_nginx_on_server_for_dmz_proxy.conf`. This isn't a style preference — if the paths drift apart, requests either 404 on the internal server, or (worse) start matching a broader/wrong `location` block than intended, silently changing what's protected. Treat the location list as one shared contract between the two files:

- Adding a new public route → add the same-named `location` block to **both** files (DMZ: real `proxy_pass`; internal: real `proxy_pass`).
- Adding a new admin route → add the same-named `location` block to **both** files (DMZ: `return 403;`; internal: IP allow-list + `proxy_pass`).
- Never add a location to only one of the two files.

## Recovering the real client IP

Because the DMZ sits between the public client and the internal server, `$remote_addr` means something different depending on which chain a request came through:

- On **public traffic**, the internal server's `$remote_addr` is the **DMZ's** IP (it's the one connecting), not the original client.
- On **admin/LAN traffic**, the internal server's `$remote_addr` **is** the real client IP, since LAN/VPN clients connect to it directly.

The internal config resolves this with a map instead of trusting either value blindly:

```nginx
map $http_x_real_ip $real_ip {
    ""      $remote_addr;      # no X-Real-IP header → direct connection, trust $remote_addr
    default $http_x_real_ip;   # X-Real-IP present → came via the DMZ, trust that instead
}
```

The DMZ, in turn, only forwards `X-Real-IP` after it has already resolved the true client IP from Cloudflare's `CF-Connecting-IP` header (via its own `set_real_ip_from` / `real_ip_header` config) — so by the time the internal server sees it, it's the real originating client, not Cloudflare's edge IP.

## Internal-only services (no DMZ counterpart at all)

Some services should never be reachable from the internet in any form — not even through a locked-down DMZ route. For these, skip the DMZ tier entirely: create a single nginx config that only exists on an internal server (the same one handling DMZ-proxied traffic, or a different internal server — anywhere **except** the DMZ box) and give every location its own LAN/VPN IP allow-list.

Reference configs: `n8n_nginx.conf` and `internal_services.conf` (landing page, Emby, Homer, Zabbix). Both:

- Use a Cloudflare DNS record with the proxy toggle **off** (see [Domain &amp; SSL setup](<5. setting a domain name with ssl cert.md>)) — or no public DNS record at all.
- Gate every `location` with `allow <LAN/VPN ranges>; deny all;`.
- Have no corresponding DMZ config — there's nothing to keep in sync, because nothing about them is ever public.

## Summary checklist

- [X] Public site → DMZ proxy config + internal config, same `location` paths in both, admin paths `403` on the DMZ.
- [X] Admin path → allow-listed to LAN/VPN on the internal config only, never proxied on the DMZ.
- [X] Internal-only service → one config, internal server only, every location IP-restricted, no DMZ config at all.
- [X] DMZ Cloudflare-only ingress (`geo`/`real_ip_header`) stays intact so nothing can hit the DMZ except through Cloudflare.
