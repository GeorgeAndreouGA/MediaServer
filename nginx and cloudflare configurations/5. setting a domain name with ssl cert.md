# Domain Name & SSL Certificate Setup (sslfree.io)

> By this point your site and services are already running on localhost via their Docker Compose files. This step exposes your website to the internet and your internal services to the LAN, using nginx as a reverse proxy with a certificate issued by **[sslfree.io](https://sslfree.io)**.
>
> We no longer use certbot. There is no ACME client running on the server and no auto-renew cron job — certificates are requested through the sslfree.io website and installed by hand.

## 1. Get a domain and point it at Cloudflare

Register (or move) your domain's DNS to **Cloudflare** — it gives DDoS protection and easy DNS management, and its proxy is the mechanism used below to decide what's public vs. internal-only.

### DNS records

In the Cloudflare dashboard, go to **DNS → Records**:

| Field        | Value                                                            |
| ------------ | ---------------------------------------------------------------- |
| Type         | `A`                                                            |
| Name         | `@` (the root — this is your domain itself)                   |
| Content      | your current public IP (kept in sync automatically — see below) |
| Proxy status | see the note below                                               |
| TTL          | Auto                                                             |

*(An `AAAA` record is the IPv6 equivalent — optional.)*

For a subdomain (n8n needs one — see [Reverse Proxy Architecture](<6. reverse proxy architecture ( dmz + internal ).md>)):

| Field        | Value              |
| ------------ | ------------------ |
| Type         | `CNAME`          |
| Name         | your subdomain     |
| Target       | your domain        |
| Proxy status | see the note below |

> **The proxy toggle (orange vs. grey cloud) is your public/internal switch:**
>
> - **Public website** → proxy **ON** (orange cloud) — traffic is routed through Cloudflare's edge.
> - **Internal-only service** → proxy **OFF** (grey cloud) — the record just resolves to the IP directly, with nothing passing through Cloudflare. This is required for anything that must stay LAN/VPN-only.
>
> Get this right per-record — it's the first of several layers that keep internal services off the public internet.

### Two DNS layers: Cloudflare vs. local DNS

There are two separate DNS zones in play here, and they follow **opposite** logic for when to use an `A` record vs. a `CNAME`:

- **Cloudflare (public DNS)** — resolves your domain for the entire internet. You only have **one public IP** (the router's WAN address), so only one record ever needs to hold it.
- **Local DNS (Pi-hole, internal)** — resolves your domain for LAN/VPN clients directly to whichever internal server actually hosts that name. Every internal server has its own distinct LAN IP.

|                                | Cloudflare (public)                                                                                                                                                                      | Local DNS (internal)                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Root domain (`<domain>.com`) | `A` → your public IP (kept current by the [dynamic-DNS script](<cloudflare configs/cloudflare script for updating dynamic public ip ( use this script for every domain you own ).sh>)) | `A` → the LAN IP of whichever internal server handles the root |
| A new subdomain                | `CNAME` → `<domain>.com` — there's only one public IP, so every subdomain aliases to the root instead of repeating it                                                              | Depends on where it actually lives — see below                   |

**The rule for local DNS:** an `A` record means "this name has its own IP"; a `CNAME` means "this name is just another name for something that already has one." So:

- Subdomain points to a **new server** (a LAN IP not already covered by an existing local record) → create an **`A` record** for it.
- Subdomain points to the **same server** as an existing record (same LAN IP) → create a **`CNAME`** to that existing name instead of duplicating the IP.

#### Worked example: `something.<domain>.com`

- **On Cloudflare:** `something.<domain>.com` → `CNAME` → `<domain>.com`. Both names ultimately resolve to the one public IP we have — there's nothing to gain from a second `A` record, and it'd be one more place to update if that public IP ever changes.
- **On local DNS**, it depends on which internal server actually runs that service:
  - Different internal server than the one serving `<domain>.com` → `something.<domain>.com` → **`A`** → that server's own LAN IP (it's a genuinely new destination).
  - Same internal server as `<domain>.com` → `something.<domain>.com` → **`CNAME`** → `<domain>.com` (which already has the `A` record locally).

Either way, once the client's local DNS resolves the name to an internal IP, the rest of the path is identical: **client → that server's firewall (UFW) → nginx** — which is where the [DMZ/internal routing](<6. reverse proxy architecture ( dmz + internal ).md>) and per-service `location` blocks take over.

### Critical exception: publicly-available (DMZ) sites get no local DNS record at all

> **Do not create an `A` or `CNAME` record in the local DNS for any domain that's served through the DMZ proxy** (see [Reverse Proxy Architecture](<6. reverse proxy architecture ( dmz + internal ).md>)) — not even to point LAN clients at the internal server directly. This is the one case where the "new server vs. same server" rule above does **not** apply.

`nginx configs/dmz-proxy/proxy_nginx_dmz.conf` only lets Cloudflare's published IP ranges through — everything else gets `return 403;` from its `geo`/`$is_allowed` check. Adding a local DNS record for the public domain only "works" if you also widen that allow-list to include your internal/LAN subnet, and that's exactly where it breaks: the Cloudflare ranges (and whatever LAN CIDR you tack on) are IPv4 only. Phones very commonly prefer IPv6 whenever it's available — both on Wi-Fi and cellular — so a phone with any IPv6 path to the DMZ slips past every rule in that allow-list and gets 403'd, while a laptop on the same network, connecting over IPv4, works perfectly. It's a real, well-documented gotcha with Cloudflare + nginx allow-lists — forgetting the IPv6 side is the single most common mistake people make locking nginx down to "Cloudflare only."

The fix is simply **not to shortcut it**: leave public-site domains out of the local DNS entirely. LAN and VPN clients then resolve the name to the same public IP as everyone else, and their traffic takes the same path as any internet visitor — **client → gateway → Cloudflare → gateway → DMZ proxy → internal server** — including the trip back out through your own router. That extra hairpin round-trip is the price of only ever having to trust one allow-list (Cloudflare's) instead of maintaining a second, IPv6-complete one for internal ranges.

### Keep the record's IP current

Add the [dynamic-DNS update script](<cloudflare configs/cloudflare script for updating dynamic public ip ( use this script for every domain you own ).sh>) to **root's** crontab, using the full path:

```bash
sudo crontab -e
# */5 * * * * /root/cloudflare/<domain>.sh
```

Use one script per domain, with that domain's API token, zone ID, and record name filled in, and `"proxied"` set to match the table above (`true` for public, `false` for internal-only — the script documents both).

Also enable **Always Use HTTPS** in the Cloudflare dashboard.

### WAF: country and bot rules

Add two custom rules per public domain (**Security → WAF → Custom rules**). This is edge-level filtering — traffic gets stopped by Cloudflare before it ever reaches the DMZ, on top of (not instead of) the DMZ's own Cloudflare-IP-only allow-list from [Reverse Proxy Architecture](<6. reverse proxy architecture ( dmz + internal ).md>):

- **Country rule** — if you only expect visitors from specific countries, restrict to them. Field: `Country`, action: `Block`, or `Managed Challenge` if you'd rather let unexpected-but-legitimate visitors through a captcha than deny them outright.
- **Bot rule** — enable **Bot Fight Mode** (**Security → Bots**), or add a custom rule that issues a `Managed Challenge` to requests with a low Bot Score. Prefer `Managed Challenge` over an outright `Block` here too — it filters out most automated traffic without also turning away real users caught by a Bot Score false positive.

Both run before a request ever reaches the DMZ — cheaper than rejecting it in nginx, and one more layer before the DMZ's own Cloudflare-only `geo` allow-list is ever exercised.

### Cloudflare's edge certificate vs. the sslfree origin certificate

For a **public** (orange-cloud) domain, two entirely different certificates are involved, terminating two different hops:

| Hop                                      | Certificate                                                                                          | Who sees/validates it |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------- |
| Visitor ↔ Cloudflare's edge             | Cloudflare's own "Universal SSL" certificate — issued and rotated automatically, nothing to do here | The visitor's browser |
| Cloudflare ↔ origin (this server's DMZ) | The **sslfree.io** certificate from this guide, installed on the DMZ                          | Cloudflare itself     |

A visitor's browser never sees the sslfree certificate for a proxied domain — only Cloudflare's own. That doesn't make the sslfree certificate optional: it's what encrypts (and, depending on the mode below, authenticates) the second hop, from Cloudflare back to your **gateway** , then to your **DMZ proxy server**.

**Set the Cloudflare SSL/TLS mode to `Full (strict)`** (**SSL/TLS → Overview**):

- `Flexible` — Cloudflare talks to the origin over **plain HTTP**. Never use this here; it makes the DMZ's entire TLS setup pointless, since the Cloudflare-to-origin hop is left unencrypted.
- `Full` — encrypts the second hop but doesn't validate the origin certificate (tolerates self-signed or expired certs). Better than nothing, but it'll silently keep working even if the sslfree certificate has quietly expired.
- `Full (strict)` — encrypts *and* validates the origin certificate against the hostname and its expiry. This is what actually gives the [&#34;renewal is manual&#34; warning](#5-lock-down-and-install-the-certificate) below teeth: if an sslfree certificate lapses, `Full (strict)` refuses to serve that domain rather than silently falling back to something insecure — which is the failure mode you want.

For **internal-only** (grey-cloud) domains, none of this applies — Cloudflare isn't in the path at all, so the sslfree certificate on that server is the only certificate involved, full stop.

## 2. Port forwarding & host firewall

On the router, forward only port 443 of the **proxy server only**:

- **443** — HTTPS

On the server's own firewall, 443 are the *only* ports ever opened to the world — see [Firewall (UFW)](<../Server set Up ( Do first )/4. ufw ( firewall ).md>).

## 3. Install nginx

```bash
sudo apt install nginx
```

## 4. Issue the certificate with sslfree.io

For each domain **and each subdomain/CNAME** (every one needs its own certificate):

1. Go to [sslfree.io](https://sslfree.io) and request a certificate for that domain/subdomain.
2. Complete domain-validation challenge it presents (DNS) .
3. Download the issued certificate — you'll get a full-chain certificate file and a private key file.

## 5. Lock down and install the certificate

```bash
sudo mkdir -p /etc/sslfree/<domain>
sudo mv fullchain.crt /etc/sslfree/<domain>/fullchain.crt
sudo mv private.key   /etc/sslfree/<domain>/private.key

sudo chown root:root /etc/sslfree/<domain>/fullchain.crt /etc/sslfree/<domain>/private.key
sudo chmod 644 /etc/sslfree/<domain>/fullchain.crt
sudo chmod 600 /etc/sslfree/<domain>/private.key
```

> **The private key must be `600`, owned by `root`.** It's the one file in this whole setup that decrypts your TLS traffic — anything more permissive means any other local user (or process) can read it.

## 6. Point nginx at the certificate

```nginx
ssl_certificate     /etc/sslfree/<domain>/fullchain.crt;
ssl_certificate_key /etc/sslfree/<domain>/private.key;
```

Enable the site and reload:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

> **Renewal is manual.** There's no certbot cron job doing this for you anymore — track each certificate's expiry yourself and repeat steps 4–6 before it lapses:
>
> ```bash
> openssl x509 -enddate -noout -in /etc/sslfree/<domain>/fullchain.crt
> ```
