# Firewall (UFW) & Docker Network Isolation

## 1. Install UFW

```bash
sudo apt update
sudo apt install ufw -y
sudo ufw enable
```

## 2. Default policy

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

## 3. Allow only the ports you need

Allow each port your services actually expose (see below for why almost nothing needs to be opened directly):

```bash
# Restrict to a specific source IP:
sudo ufw allow proto <protocol> from <IP_ADDRESS> to any port <PORT_NUMBER>

# Same, but rate-limited (helps against brute force / DDoS):
sudo ufw limit proto <protocol> from <IP_ADDRESS> to any port <PORT_NUMBER>

# Allow from anywhere:
sudo ufw allow <PORT_NUMBER>
```

Apply and verify:

```bash
sudo ufw reload
sudo ufw status
```

> **We only port-forward 80 and 443 on the router.** Every other exposed port is reached over the Tailscale VPN — see [VPN (Tailscale)](<6. vpn ( tailscale ).md>).

## How Docker interacts with the host firewall

> **Critical:** UFW does **not** govern Docker's published ports. Docker manages its own `iptables` rules, so a container port published in a `docker-compose.yaml` bypasses UFW entirely unless you account for this.

There are effectively two firewalls on the host: UFW (the host's) and Docker's own `iptables` rules. Rather than trying to reconcile the two, this setup sidesteps the conflict entirely:

1. **Bind every container's host port to loopback only** — `127.0.0.1:<port>:<container-port>` in the compose file, never the server's LAN IP. This makes the service reachable only from the server itself: not from anywhere else on the network, and not through Docker's `iptables` rules.
2. **Put nginx in front of it** as a reverse proxy, forwarding from the server's private IP (on a port you choose) to the container's loopback address, with nginx handling per-client IP restrictions.
3. **Open that nginx port in UFW**, scoped to only the IPs that should have access.

Traffic then passes through two independent filters — **UFW first** (network-layer allow-listing), then  **nginx** (application-layer routing + IP allow-listing). The container's actual port is never exposed to the LAN or the internet, only to the loopback interface, which only the host itself can reach.

This also means hitting `<server-ip>:<container-port>` directly from another device on the LAN will **not** work, even from an allow-listed device — the host port is only bound to `127.0.0.1`. Access has to go through nginx's port instead.

In the nginx server block, this looks like:

```nginx
listen <nginx-port> ssl http2;

location /emby {
    proxy_pass http://127.0.0.1:8096/;
}
```

See the nginx configs for the full reverse-proxy setup.
